# v0.2 — the kb submodule is gone

The kb is now an ordinary gitignored clone at `kb/`, not a git submodule.
No submodule pointer to bump, no `submodules: recursive` in CI.

## What happens on `rcorn update` / `rcorn init`

Repos still on the submodule layout are migrated in place:

1. The migration REFUSES to run while the old `kb/` has uncommitted or
   unpushed work — publish it first (`rcorn kb publish`).
2. The submodule is deregistered, the gitlink and `.gitmodules` entry are
   removed (removal left staged for you to commit), `.git/modules/kb` is
   set aside as `.git/modules/kb.pre-clone-migration`, and `kb/` is
   re-cloned fresh from `REINICORN_KB_REMOTE`.
3. `kb/` is added to `.gitignore`, `REINICORN_KB_REMOTE` is recorded in
   `.reinicorn-config`, and the migration installs the `pre-commit` hook
   that refuses any staged path under `kb/` — automatically, as part of
   `rcorn update` / `rcorn init`. Other clones of the same repo each need
   their own `rcorn update` to get the hook too (hooks are per-clone, not
   shared through git).

Commit the staged changes when it finishes:

    git add .gitignore .reinicorn-config
    git commit -m "chore: migrate kb from submodule to clone"

If `.gitmodules` still exists afterwards (it declared submodules besides
`kb`, so it survived with just the `kb` section removed), add it too —
`git add .gitmodules`. When `kb` was the only entry, the file's deletion
was already staged automatically and `git add .gitmodules` would fail
with "pathspec did not match any files". The migration's own output
tells you exactly which `git add` to run — you can just paste that.

## CI

Drop `submodules: recursive` from `actions/checkout` and clone instead:

    - name: Clone kb
      run: git clone --depth 1 <your-kb-url> kb
