# v0.3 — superpowers forks become an adapter

The 13 vendored superpowers skills are no longer part of the package. They
now live in the bundled 'superpowers' skill-set adapter, installed on
demand and tracked by its own lockfile instead of the asset manifest.

## Skills

- Vendored forks (brainstorming, systematic-debugging, writing-plans, ...)
  are replaced by the 'superpowers' skill-set adapter — install with
  `rcorn skills install superpowers`.
- `update-superpowers` is removed; there is no upstream-sync skill to run
  by hand anymore — use `rcorn skills update` instead.
- New `rcorn skills` command family: `install`, `status`, `update`, `list`.

## What happens on `rcorn update`

A project still carrying the old forks (tracked in its asset manifest,
no skillset lock yet) is offered a one-time migration:

    Legacy superpowers skill forks detected (shipped by an older Reinicorn).
    These are now provided by the 'superpowers' skill-set adapter instead.
    Migrate now? Installs the adapter (network required) and removes the old
    copies; locally modified files are kept. Answer 'n' to keep the old forks
    and never ask again (rcorn skills install superpowers migrates later). [y/N]

Answer 'y' to install the adapter and remove the old copies — locally
modified files are always kept, never silently deleted. Answer 'n' to keep
the forks and skip the offer for good; `rcorn skills install superpowers`
migrates later, on your own schedule.

## Breaking changes

- `.agents/skills` ownership is split: native skills (`using-reinicorn`,
  `populate-agents-md`) stay `rcorn update`-managed; adapter-installed
  skills are `rcorn skills`-managed instead — tracked by the skillset
  lockfile, not the asset manifest. Whether to commit or gitignore them is
  the repo owner's choice.
- `using-reinicorn` methodology-neutral rewrite: it no longer names a
  specific methodology skill, deferring instead to the generated
  `references/skillset-wiring.md` for which skill(s) to invoke per doc type.
